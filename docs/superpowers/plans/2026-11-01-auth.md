# Auth (Email/Password) Implementation Plan

**Goal:** Add email/password auth with registration, email verification, login, logout, and a protected dashboard, backed by a local SQLite file.

**Architecture:** Remix-native. A SQLite `data-table` database holds `users` and a separate `user_passwords` table. Session middleware persists login state; authenticated sessions are stored in the database (see the sessions plan) while anonymous sessions stay in the signed cookie. Credentials provider verifies email/password/verification. CSRF middleware protects form posts. Routes are `form()` pairs for login/register plus plain routes for verify/logout/dashboard.

**Tech Stack:** remix (router, middleware, data-table, data-schema, component), Node crypto (scrypt), SQLite (node:sqlite via remix).

**Spec:** `docs/superpowers/specs/2026-11-01-auth-design.md`

## Global Constraints

- Package manager/runtime: Node + npm; no new dependencies.
- Strict TypeScript; `verbatimModuleSyntax` (use `import type`).
- Conventional Commits for each task.
- Passwords hashed with Node crypto (scrypt).
- Session cookie: name `__session`, signed with `SESSION_SECRET`, httpOnly, sameSite `lax`, path `/`, 30-day max age. Production must set `SESSION_SECRET`.
- Verification token expiry: 24 hours.
- Password minimum length: 8.
- Emails are trimmed and lowercased before storage and lookup.
- Tests run against an in-memory SQLite database (`NODE_ENV=test`).

## Review Focus

- Unverified user attempting login must be rejected with a generic error (no email enumeration).
- Expired/invalid verification token must not verify or crash.
- Password hash must never appear in dashboard/user-loading code paths.
- CSRF token missing/invalid must reject POSTs.
- Logout must destroy server-side session state, not just unset one field.
- Duplicate email must not create a second user or a 500.
- Protection on one controller does not flow into nested route maps; each protected controller declares `requireAuth()`.
